# «لولو الإدارة» — making the admin assistant actually useful

**Date:** 2026-08-27 · **Status:** approved, not implemented
**Owner complaint:** «يجاوب غلط أو ناقص · ما يكدر يسوي أشياء · الشكل والاستعمال · need more
actions and more info about db and staff and more straight answers»

## 0. What is actually there today

Two separate admin AI surfaces, both live, both reachable, and they are **not** the same code:

| | `/admin` widget | `/admin/assistant` — «لولو الإدارة» |
|---|---|---|
| Controller | `adminAnalyticsChatController.js` (149 ln) | `adminConsoleController.js` (315 ln) |
| Answer guard | none | `lib/adminAnswerGuard.js` |
| Actions | none | 6, via `lib/adminActions.js` |
| Suggestions | none | `lib/adminSuggestions.js`, model-free |
| History | not offered | stored, served **and rendered** (15 turns) |
| Refusal text | **hardcoded, names 8 of 21 metrics** | accurate, generated by hand but complete |

Both share `lib/adminMetrics.js` (21 metrics) and both route with one cheap JSON call.

## 1. The four real defects

**(a) One metric per question.** `adminConsoleController.js:178` —
`route.kind === 'metric' && route.key` selects exactly one key. «كم بعت هذا الشهر ومنو أحسن
ممثل؟» returns half an answer, and the admin cannot tell that half was dropped.

**(b) The model has no memory, but the screen pretends it does.** `sessionKey: null` (line
127) and both `ai.complete` calls (lines 139, 195) are handed `system + the current question`
only. Meanwhile the page loads and renders the last 15 turns, so it *looks* like a thread.
«وشنو عن الشهر الماضي؟» is therefore unanswerable — the worst kind of failure, because the UI
promised otherwise.

**(c) The `/admin` widget's refusal is stale and false.**
`adminAnalyticsChatController.js:105` hardcodes eight capabilities. `METRICS` has 21. The
router prompt is fine — it is built by `metrics.catalogForPrompt()` — so the model knows
things the sentence tells the owner it cannot do.

**(d) The catalogue is thin where the owner's questions are.** 21 metrics, and staff is
covered by `staff_today` / `staff_not_opened` / `staff_worked_ranking` / `staff_app_usage`
only. Nothing answers lateness, deductions, breaks, salary balances, shelf state, or a single
named person's month.

## 2. What we are building

### 2.1 Retire the `/admin` widget — do not fix it

Two assistants on two screens is why (c) exists and why "straight answers" is inconsistent:
the owner gets a guarded answer on one screen and an unguarded one on the other. Point
`/admin`'s widget at the console's `ask` endpoint and delete
`adminAnalyticsChatController.js` and its route. One surface, one guard, one history, one
budget line.

⚠️ Check `test/aiChat.test.js` — it imports that controller's `_internals.parseRoute`.

### 2.2 Multi-metric answers

The router returns `keys: string[]` (max 3) instead of `key: string`. Run them with
`Promise.all`, concatenate the fact blocks under their own labels, phrase once.

- Unknown keys are dropped, not fatal — a 2-of-3 answer beats a refusal.
- **The guard must run over the joined answer**, and this is the risk the change introduces:
  `lib/adminAnswerGuard.js` rejects any number absent from the facts we computed, so its input
  becomes the *union* of all fact blocks. Widening its input is exactly how a guard silently
  stops guarding — the join must be assembled once and handed to both the phrasing call and
  the guard, never assembled twice.
- `intent` logged as the joined keys (`"revenue_summary+top_reps"`) so
  `ai_chat_messages.intent` stays the record of what was asked for.
- Keep `keys: []` meaning "cannot answer" — the NULL-intent backlog signal survives.

### 2.3 Real memory

Mint a real `sessionKey` per admin (the existing `lib/anonSession.js` HMAC shape, keyed on the
admin's user id — it needs no new dependency) and feed the **last 2 turns** into the router
call only.

**The phrasing call must NOT receive history.** Its whole safety property is that it sees only
numbers we computed this request; giving it a previous answer hands it numbers that are no
longer being verified against anything, and `adminAnswerGuard` would then reject its own
prior output. Memory belongs to routing — "what does «الشهر الماضي» refer to" — and nowhere
else. Write this in the file, next to the call.

### 2.4 More metrics — driven by data, not by guessing

`ai_chat_messages` already records every unanswerable question with `intent IS NULL`. **Read
that table first** and let it order the work; it exists precisely to be this backlog.

The ones already known to be missing, all from tables that exist:

| Key | Answers |
|---|---|
| `staff_attendance_month` | حضور/غياب/تأخير موظف معيّن هذا الشهر — `staff_attendance_records` |
| `staff_deductions` | الخصومات وأسبابها — `staff_salary_transactions` + `staff_attendance_breaks` |
| `staff_breaks_month` | الفتحات: عدد، دقائق، المجاني والمخصوم |
| `salary_balances` | رصيد كل موظف الآن — `staff_salaries` + transactions |
| `shelf_state` | الرفوف: كم خانة مشغولة، شنو ينتظر |
| `person_summary` | كل شي عن شخص واحد بالاسم — the "straight answer" shape |

⚠️ Every money metric goes through `lib/counts.js` (`shopIncomeExpr` · `repMarginExpr` ·
`settledMoney`). A metric that writes its own `SUM(orders.profit)` reports the **rep's**
margin as the shop's — the exact failure that file's header warns about, and the one
`test/assistantMoneyAgreement.test.js` exists to catch. Extend that test to any new money
metric.

### 2.5 More actions

Current six: `extend_rep_deadline` · `set_order_cost` · `approve_break` · `reject_break` ·
`add_staff_bonus` · `set_staff_goal`.

Candidates, in the order the owner is most likely to want them:
`add_staff_deduction` (the mirror of the bonus, with a mandatory reason) ·
`set_workshop_rate` · `mark_holiday` (needs piece 4's `staff_holidays`) ·
`extend_order_deadline` · `set_product_price`.

Every one keeps the existing protocol without exception: **propose → signed proposal → the
admin types تأكيد → execute**. `lib/adminActions.js` re-derives and re-validates every
parameter at execution; nothing in the request body is trusted. An action that writes money or
sends a message to a customer does not get added without that round trip.

**Explicitly not added:** anything that sends a push to students. `lib/pushBroadcast.js`'s
closed link allowlist and typed-back recipient count are what stand between one compromised
admin session and a phishing message wearing the shop's name in front of 1,100+ accounts. A
model must not be a path to that, however well guarded.

### 2.6 The screen

`frontend/app/admin/assistant/page.tsx` (506 lines) at **390px** — never yet looked at on a
phone across four sessions, per HANDOFF. What to check: the suggestion cards, the confirm
card, the report table, and the input row.

Plus: show which metrics an answer came from (the `label`s are already returned), and keep
the facts list visible — it is what makes the prose auditable and is already shipped.

## 4. Testing

- Router returns 3 keys → all three fact blocks present, phrased once, guard sees the union.
- One bad key among three → the other two still answer.
- The guard **rejects** a number that appears in no fact block, on a joined answer. Red/green:
  the test must fail if the guard is handed only the first block.
- A follow-up question resolves against the previous turn; the phrasing call's message array
  contains no prior turn.
- Every new money metric agrees with the dashboard (`assistantMoneyAgreement.test.js`).
- Every new action refuses to execute without a valid signed proposal.
